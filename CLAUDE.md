# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Monorepo for a multi-tenant School ERP SaaS. `backend/` is a NestJS 11 API (TypeORM 1.x + PostgreSQL), `frontend/` is a Next.js 16 App Router app (React 19, Tailwind v4, shadcn/radix UI, TanStack Query, NextAuth v5). The two are separate npm projects with no root workspace, so run commands from inside each directory. `doc/` holds product and design docs: `prd.md` (the product spec and source of truth), DB designs (`db-schema.md`, `academic-db.md`, `student-db.md`) and an example frontend menu.

`frontend/CLAUDE.md` → `frontend/AGENTS.md` warns that this Next.js version has breaking changes compared with your training data. Read the relevant guide in `frontend/node_modules/next/dist/docs/` before writing frontend code. For example, middleware now lives in `src/proxy.ts`, not `middleware.ts`.

## Commands

Local infrastructure (repo root): `docker compose up -d` starts Postgres (host port 5433), pgAdmin (:5050), Redis (:6379), RedisInsight (:5540), MinIO (S3 API :9000, console :9001; a `minio-init` job creates the `school-erp` bucket) and Mailpit (SMTP :1025, UI :8025). Overrides go in a root `.env` (see `.env.docker.example`).

Backend (`cd backend`, API on `PORT=3900` with global prefix `/api`, Swagger at `/api/docs`):

```bash
npm run start:dev                      # watch mode
npm run build
npm run lint                           # eslint --fix
npm run format                         # prettier
npm test                               # unit tests (*.spec.ts under src/)
npm test -- src/modules/students/services/student.service.spec.ts   # single file
npm test -- -t "creates a student"     # single test by name (the scripts set NODE_OPTIONS=--experimental-vm-modules, which puppeteer 25 needs; plain `npx jest` fails to load it)
npm run lint:check && npm run format:check && npm run typecheck   # what CI checks (no --fix)
npm run test:release                   # PRD 11.5 release suites: tests tagged [tenant-isolation], [gpa-regression], [fee-regression]
npm run docs:error-codes              # regenerate doc/error-codes.md (a unit spec fails when it is stale)
npm run test:e2e                       # test/*.e2e-spec.ts; needs a live Postgres. Uses its own <DB_NAME>_e2e database (created on first run) and a restricted app role so RLS applies (test/e2e-env.ts)
```

Frontend (`cd frontend`, http://localhost:3000):

```bash
npm run dev
npm run build
npm run lint
```

The frontend has no test runner.

CI (`.github/workflows/ci.yml`) runs on every PR and push to `main`: backend format/lint/typecheck/unit/build, backend e2e against Postgres 17 + Redis service containers (`--runInBand`), and the frontend build. A test that checks cross-school isolation carries `[tenant-isolation]` in its `describe`/`it` name; the grading and fee regression suites use `[gpa-regression]` / `[fee-regression]`. CI also checks `dist/main.js` exists and runs `npm audit --omit=dev --audit-level=high`. `doc/release-checklist.md` maps each PRD 11.5 criterion to its suite or check; `doc/operations.md` is the runbook (monitoring, backups and restore, pilot onboarding).

Local env: the backend reads `.env` and then `.env.${NODE_ENV}` (`.env.development` by default), validated by Joi in `src/config/env.validation.ts`. Mail defaults to Mailpit on `localhost:1025`. `CORS_ORIGIN` is required in production and accepts `https://*.example.com` entries for tenant subdomains (`src/config/cors.ts`). Tenant subdomains use `lvh.me` in dev (e.g. `http://acme.lvh.me:3000`). See `backend/.env.example` and `frontend/.env.example`.

## Backend architecture

### Shared-schema multi-tenancy with `org_id` + RLS (`src/tenancy/`)

- **One schema (`public`) for everything.** A school is an `Organization` (`organizations` table, `modules/organizations/`). All feature modules sit flat under `src/modules/` (no platform/tenanted split); what makes an entity school-owned is extending `OrgScopedEntity`, not its folder. The glob `src/modules/**/entities/*.entity.ts` is loaded by the root DataSource and the tenant pool, so you don't register entities anywhere.
- **Every tenanted entity extends `OrgScopedEntity`** (`src/tenancy/org-scoped.entity.ts`), which adds `org_id` with a cascading FK to `organizations` (deleting an org deletes all its data). Per-org uniqueness must include `orgId`, e.g. `@Index('uq_classes_org_name', ['orgId', 'name'], { unique: true })`. Never put `unique: true` on a tenanted column.
- **Users are global**: one `users` table (one login across schools). Per-school state lives on `memberships` (`org_id`, `role`, `is_admin` = school admin, `status`) and `user_roles` (org-scoped). `auth_tokens` is shared; `org_id` is null for platform-issued tokens and set for school-issued ones (incl. `activation`).
- **Request flow**:
  1. `TenantMiddleware` (applied in `AppModule.configure`) resolves the org from the `x-tenant-id` header (a slug), then the subdomain, then a custom domain (`organization_domains`, only `verified`/`active` rows). Lookups are cached in memory. Only operational schools resolve (`isOperationalOrganization`: `trial`, `active`, `past_due`); use that helper rather than comparing with `ACTIVE`. It sets `req.orgId` / `req.orgSlug` (`RequestWithOrg`).
  2. The request-scoped `TENANT_DATASOURCE` provider (in `TenancyModule`) takes a QueryRunner from the tenant pool, runs `set_config('app.org_id', <orgId>)`, and returns a `TenantDataSourceProxy` (which exposes `orgId`).
  3. The global `TenantCleanupInterceptor` resets the setting and releases the QueryRunner after the response.
- **Isolation is enforced twice**:
  - App level: `BaseTenantRepository` wraps `this.repo` with `scopeRepository` (`org-scoped-repository.ts`) for entities that have `orgId`, so `find*`/`count`/aggregates/`save`/`create`/`update`/`delete`/`increment` are pinned to the org automatically, `remove` only accepts entities of the org, and unscoped escape hatches (`upsert`, `preload`, `query`, `manager`, …) throw. The proxy fails closed: a TypeORM `Repository` method with no rule throws (a spec checks every method is classified, so a TypeORM upgrade that adds one fails `npm test`). **Query builders are not rewritten**: add `.andWhere('alias.orgId = :orgId', { orgId: this.orgId })` yourself.
  - TypeORM 1.x throws on `null` or `undefined` in `find*`/`update`/`delete` where clauses (`INVALID_WHERE_VALUES_BEHAVIOR` in `database/database.constants.ts`). Scoped repositories drop `undefined` keys, so optional filters can be left unset; match NULL with `IsNull()`. Find options use object form (`relations: { user: true }`, `select: { id: true }`), not string arrays.
  - Database level: Postgres row-level security (`rls.ts`) on every table with a NOT NULL `org_id` except platform tables listed in `PLATFORM_TABLES_WITH_ORG_ID` (e.g. `organization_slug_history`), policy `org_isolation` comparing against `current_setting('app.org_id')` (unset → no rows). The tenant pool connects as the restricted role `DB_APP_USERNAME`; the root connection (table owner) bypasses RLS and is used for platform code, org provisioning and migrations. Without `DB_APP_USERNAME` the pool falls back to the owner and RLS does not apply (a warning is logged).
- **App role grants**: the restricted role gets DML only on the org-scoped tables plus `users` and `auth_tokens` (`rls.ts` in dev, the `AppRoleGrants` migration in production). A migration that adds a tenanted table must enable RLS on it and grant the app role. `audit_logs` is append-only: the app role gets SELECT and INSERT only (`APP_ROLE_APPEND_ONLY_TABLES`).
- **Platform data read by tenants**: Bangladesh divisions/districts/upazilas (`geo_*`, `modules/geo/`, served from `~/shared/geo/bd-geo.data`) are platform tables without `org_id`; addresses reference them by id.
- **Platform routes must be excluded from `TenantMiddleware`**: when you add a platform or public route (`organizations`, `memberships`, `platform/auth`, `platform/users`, `platform/audit-logs`, `platform/plans`, `oauth`, `public`, `health`, `metrics`, `dev/mail`), add it to the `.exclude(...)` list in `src/app.module.ts`.
- **Tenanted repositories** extend `BaseTenantRepository<T>` and inject `@Inject(TENANT_DATASOURCE) ds: TenantDataSourceProxy`. Never use `@InjectRepository` for org-scoped entities. Because `TENANT_DATASOURCE` is request-scoped, every repository, service and controller that depends on it is request-scoped too. For multi-step writes, inject `TENANT_DATASOURCE` into the service and wrap them in `ds.runInTransaction(async () => …)`: all tenant repositories of the request share its QueryRunner, so they join the transaction automatically (nested calls become savepoints). In unit tests pass `fakeTenantDataSource()` (`tenancy/tenant-datasource.testing.ts`). Global accounts are read through `AccountRepository`, org members through `MemberRepository` (`modules/users/repositories/`).
- **Schema changes**: migrations live in `src/migrations/` (`npm run db:generate` / `db:migrate`, via `src/database/public.datasource.ts`). Every schema change needs one; don't edit migrations that have already run, add a new one (see `DropSampleModules`).
  - In dev with `DB_SYNC=true`, the root DataSource syncs every table; then (non-production) `TenancyModule` creates the app role if missing, enables RLS, (re)creates the policies and grants the app role DML.
  - Organization creation (`OrganizationService`) runs in one transaction: insert the org, seed system roles (`RbacSeederService.seedSystemRoles(manager, orgId)`), and provision the owner (`OwnerProvisioningService.provisionOwner(manager, …)`: OWNER membership with `isAdmin`, admin role, activation token). The activation email is sent after commit.
  - Production must use migrations, including the RLS policies/grants from `rls.ts` and creating the app role (LOGIN NOSUPERUSER NOBYPASSRLS, not the table owner).

### Auth and RBAC

- **Two JWT realms**:
  - Platform (`PlatformJwtAuthGuard` / `'platform-jwt'`, plus `PlatformAdminGuard`, in `src/common/guards/`), used for super-admin and organization management. Platform tokens never carry `orgId`; `PlatformJwtStrategy` rejects tokens that do.
  - Tenant (`JwtAuthGuard` in `modules/auth/guards/`), used for everything inside a school. Payload `{ sub, orgId, isAdmin, sid, mcp? }`; `JwtStrategy` rejects tokens whose `orgId` differs from `req.orgId`. Login checks the global password (`CredentialService`: email or phone, lockout after 5 failures), then requires an ACTIVE membership in the org.
- **Accounts and sessions**: an account has an email and/or a phone, both normalized (`common/identity/identifier.ts`). Every sign-in is a session (`SessionService`, table `user_sessions`): access tokens carry its id as `sid`, both strategies refuse revoked sessions, refresh tokens rotate and a reused one revokes the whole sign-in. Sessions belong to one school (or the platform, `orgId` null). `SessionService` lives in its own `SessionModule` (`modules/auth/session.module.ts`) so `UserModule`/`MembershipModule` can use it: anything that shrinks a member's access (remove, suspend, revoke school admin, demote an owner) calls `revokeAllForUserInOrg`, because `isAdmin` is in the access token. Add people with `POST /users/invite` (activation link, or a slip password for phone-only), or staff from the directory with `POST /employees/:id/invite` (same flow, role defaulting to the designation's `default_role_id`, links `employees.user_id`). Code that makes accounts calls `InviteService.provision(...)`, which joins the caller's transaction and returns a `sendMail()` to call after it commits; guardians and qualifying students get portal accounts that way (`portalRole`, given through `RoleService.assignPortalRole` without the escalation check), and `issueSlip(userId)` prints a password for phone-only ones. An account made without a password gets one shared unusable hash and `password_set = false`; a password set by someone else sets `must_change_password`, and the guards then allow only routes marked `@AllowPendingPasswordChange()`. A registered but unverified (PENDING) account is never linked as-is: an invite resets its password, and tenant sign-in refuses it (`ACCOUNT_PENDING`). Activation never replaces a password the account owner chose (`CredentialService.hasOwnPassword`); it asks for that password instead.
- **Google sign-in** (`modules/oauth/`, doc/domains-and-routing.md 5a): every host starts at `GET /oauth/google/start?return=<host>&next=&intent=signin|signup`; Google calls back to one URL on the product domain, and the browser returns to the starting host with a handoff code (`/auth/handoff`, or `POST /platform/auth/handoff/exchange` on the admin host). It finds the account by linked identity (`user_identities`, `IdentityService`) or verified email, never creates a membership, and gives non-members the same answer as unknown accounts. `return` must be a host we serve and `next` a same-host path (`safeNext`). Accounts created through Google have `password_set = false`, and unlinking needs a password. Off (404 `GOOGLE_SIGNIN_DISABLED`) until `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are set.
- **Signup and onboarding**: self-serve signup (`modules/signup/`, `POST /public/signup` then `/verify`) creates the school only after email (or Google) verification, on a 30-day trial, through `OrganizationService.createForSignup`. `organizations.onboarding_completed_at` (set by `POST /onboarding/complete|skip`, shown in `GET /auth/me`) drives the frontend's onboarding gate; the checklist is computed from real data.
- **Tenanted controller pattern**:
  - `@UseGuards(JwtAuthGuard, PermissionsGuard)` plus `@RequirePermissions(PERMISSIONS.X)` per handler.
  - Swagger decorators: `@ApiBearerAuth('tenant-jwt')` and `@ApiHeader({ name: 'x-tenant-id' })`.
- **Permission catalog**: permissions are code-defined in `modules/rbac/permissions.catalog.ts`, using `resource:action` keys.
  - Roles are stored per tenant and reference these keys. System roles are seeded from `system-roles.seed.ts`.
  - Members with `isAdmin` (from their membership, carried in the JWT) bypass permission checks.
  - No escalation: outside school admins, `RoleService` only lets a user create, edit, clone, assign or unassign roles whose keys they hold themselves (school-wide reach for a school-wide role; `GRANT_EXCEEDS_OWN`). Pre-check requested role ids with `RoleService.findAssignable`. Only school admins change or remove a school admin. System roles keep their scope, the `admin` role keeps every staff key, and a role is either portal-only (`portal:*`, guardian/student) or staff-only.
  - A new feature needs new catalog entries, plus seed updates if system roles should get them (and a migration that updates existing orgs' system roles, like `AlignSystemRoles`).
  - System roles (PRD 6.3): `admin`, `principal`, `accountant`, `teacher`, `class_teacher`, `receptionist`, `librarian`, `committee_member`, `student`, `guardian`. Guardian and student hold only `portal:*` keys, so they're refused on staff endpoints. `POST /roles/:id/clone` copies a role into a custom one.
- **Scope rules**: `roles.scope` is `school` or `assigned` (seeded `teacher`/`class_teacher`); a user's scope for a key is the widest among the roles granting it (`PermissionResolverService.getPermissionScopes`). Endpoints that read or write section or subject data inject the request-scoped `AccessScope` (`modules/access-scope/`, import `AccessScopeModule`) after `PermissionsGuard`: `sections(key)` returns `null` for unrestricted or the section ids the user has an assignment in effect today (school time zone, from `TeachingService`), `subjectAssignments(key)` the `{ sectionId, classSubjectId }` pairs they teach, and `canAccessSection(key, sectionId)`/`canAccessSubject` check one. Lists filter by the answer, single reads 404 outside it. `SectionModule`, `TeachingModule` and `AccessScopeModule` import each other with `forwardRef` (only the modules form a cycle).

### Conventions

- **Imports**: relative paths inside a module; `~/modules/…`, `~/common/…`, `~/tenancy/…`, `~/shared/…`, `~/utils/…` and `~/config` across areas (no `src/…` imports in `src/`). `req.user` is typed as `AuthUser` (`common/auth/auth-user.ts`), which both JWT strategies return.
- **Path aliases** (tsconfig and Jest `moduleNameMapper`, which must be kept in sync, including `test/jest-e2e.json`): `~/common/*`, `~/config`, `~/utils/*`, `~/shared/*`, `~/tenancy/*`, `~/modules/*` → `src/modules/*`, and `src/*`.
- **Feature module layout**: `<feature>.module.ts`, `controllers/`, `services/`, `repositories/`, `entities/`, `dto/`, `enums/` (rbac also has `guards/` and `decorators/`). A module with a single controller, service and repository keeps those three flat; as soon as it has more than one of any, it uses the subfolders. `auth/` and `users/` each hold both realms in one module: platform pieces are prefixed `platform-`/`Platform*` (e.g. `PlatformAuthController` on `/platform/auth`, `PlatformUserController` on `/platform/users`), tenant pieces are unprefixed or `org-`/`Org*` (`AuthController` on `/auth`, `OrgUserController`/`OrgUserService` on `/users`). Every module must be imported in `src/app.module.ts`.
- **Module boundaries**: modules talk to each other through exported services (e.g. `AcademicYearService.findById` to check a referenced id, `RoleService.findSystemRole`), never through another module's repository; modules export services, not repositories. The one exception is `UserModule` exporting `AccountRepository`/`MemberRepository` for `AuthModule`'s password flows. `RbacModule` knows nothing about users: the `/users/:userId/roles` endpoints live in `UserModule` (`OrgUserService.assignRole` checks membership), and `OwnerProvisioningService` is provided by `AuthModule`. `src/app.module.spec.ts` boots the whole AppModule with stubbed DataSources, so a missing import/export fails `npm test`.
- **Response envelope**: handlers return plain data; the global `ResponseEnvelopeInterceptor` (`common/interceptors/`, registered in `src/app.setup.ts`) wraps it as `{ success, statusCode, message, data }`, with the message from `@ResponseMessage('…')` and `@RawResponse()` to opt out (health, HTML). Errors come out of `GlobalExceptionFilter` as `{ success: false, statusCode, message, … }`. The frontend axios client unwraps `data`.
- **Pagination**: list endpoints for school data take `?page=&limit=` (filter DTOs extend `PaginationQueryDto`, default 20, max 100); repositories return `this.findPage(options, page)` and the envelope gains `meta: { page, limit, total, totalPages }` next to `data`, which stays a plain array.
- **Global pipes**: `ValidationPipe` runs with `whitelist`, `forbidNonWhitelisted` and `transform`, so unknown DTO fields cause a 400. `ClassSerializerInterceptor` is global (use `@Exclude` on entity fields). Errors go through `GlobalExceptionFilter`.
- **Logging**: `nestjs-pino` (`shared/logging/`) replaces Nest's logger, so use `new Logger(Context)` from `@nestjs/common` as usual. Lines are JSON (pretty in development), carry the request's `reqId` (`x-request-id`, set by `RequestIdMiddleware`) and, inside handlers, `orgId`/`userId`; each request ends with one `request completed` line. Never log secrets; `authorization`/`cookie` headers are redacted. `LOG_LEVEL` sets the level (tests default to `silent`).
- **Academic structure** (PRD 6.4): classes are permanent; a section belongs to one class and one session (`sections.academic_year_id`, `class_id`, optional `shift_id`/`room_id`), so a section id alone identifies both. Enrollments must use a section of their class and session, and block deleting it. Class subjects carry `subject_type` (compulsory/optional/fourth/elective), an optional `subject_group_id` and CQ/MCQ/practical/written/oral `class_subject_components`. Sessions have required, non-overlapping dates. Teacher assignments (`class_teachers`, `subject_teachers` → `class_subject_id`) are effective-dated: a change ends the current row (`effective_to`, inclusive) and opens a new one, ended rows are history (no edit, no delete), and "current" unique keys are partial on `effective_to IS NULL`. Session rollover (`POST /academic-years/:id/rollover`, `RolloverModule`) runs as an `academic`-queue job through each feature's `copyToYear`; it never touches enrollments.
- **Students** (PRD 6.6): the student ID (`admission_number`) comes from `numbering.studentId`, counted per rendered prefix (`patternScope`); typing one needs `numbering.allowManualStudentId`. Status changes only through `POST /students/:id/status` (transition table in `student-status.enum.ts`, history in `student_status_history`, closes the current enrollment). Student endpoints, including every `/students/:id/...` sub-resource, check `StudentScope.assert(key, studentId)` (404 outside the caller's sections). Health, disciplinary and counselling notes need `student_notes:read_sensitive`, filtered in the repository. Guardian phones are normalized and unique per school (the import match key). Promotion is a batch (draft → preview/overrides → commit job → rollback within 24 h). Excel imports implement the `Importer` contract (`modules/imports/importers/`): template columns, row checks, and a `commitRow` that runs on a savepoint.
- **Attendance** (PRD 6.7): a register is one section and day (`attendance_registers`, plus `period_id` when `attendance.mode` is `period`) with one record per student; the five system statuses are code-defined (`SYSTEM_STATUSES`), schools add their own in `attendance_statuses` (`counts_as` folds them into the math in `attendance-math.ts`). Writes go through `AttendanceService.submit` only: holidays (`modules/holidays/`) and weekend days are refused, days past `lockAfterDays` need `attendance:edit_locked`, and changing a recorded status (or an approved leave's Leave) needs a reason and writes `attendance_corrections`. Approved student leave sets Leave in registers already taken. Each submit records `attendance.submitted` in the `domain_events` outbox (`DomainEventService.record`, same transaction) for the Phase 1b alerts. Leave decisions belong to the class teacher (`AccessScope.homeSections`).
- **Exams and results** (PRD 6.9): grading is the pure engine in `modules/grading/engine/` (no Nest/DB; `[gpa-regression]` suite) fed by `GradingService.schemeFor(year, class)` (the class's `class_grading`, else the default system). `modules/exams/` holds exams, exam subjects (copied from class subjects, frozen once marks exist), mark sheets (one per exam subject and section) and results. Who sits a subject is `takesSubject` (compulsory for everyone in the group, others only when chosen in `student_subjects`). Sheets move Draft → Submitted → (Verified, with `results.verifyStep`) → Approved → Published only through `MarkSheetService`; approved sheets are read-only until reopened, and mark changes after the first submit are audited with old and new values. Results belong to a result definition (each exam's own, made when it opens, or a weighted combination); they tabulate as a job once every sheet is approved and publish only while current. Subject teachers enter marks (`canAccessSubject(results:enter)`); class-wide actions need the key school-wide.
- **Fees** (PRD 6.10, `modules/fees/`): money is `bigint` minor units read through `MoneyColumn` (`~/shared/database/numeric-column`); the arithmetic is pure in `fees/domain/fee-math.ts` (`[fee-regression]` suite). Invoice lines hold `net`, `adjusted`, `allocated` and `refunded` (outstanding = net − adjusted − allocated + refunded); any transaction that changes lines ends with `InvoiceTotalsService.refresh`. Payments are allocated in the transaction that locks their lines and gets the receipt number, and are never edited or deleted: cancelling the receipt reverses them. Refunds, waivers, corrections and student discounts apply only once approved (`fees:approve_waiver`). Money movements write `ledger_entries` in the same transaction. `FeeScheduler` (hourly, per school) bills on the billing day, adds late fines, records due reminders and runs the 02:00 integrity check.
- **Notices, notifications and the portal** (PRD 6.13/6.14): send notifications only through `NotificationService.notify({ userIds, key, vars, link })` (in-app rows, emails on the `notifications` queue, `delivery_logs`, per-school `notification_templates` over the code defaults in `notifications/notification-templates.ts`). Events that should reach families are recorded in the `domain_events` outbox and turned into notifications by `EventDispatcherService` (run every minute by `CommunicationScheduler`); add a handler there for a new event. Notice audiences resolve through `AudienceService` (`viewer` for feeds, `recipients` for sends). Every `/portal/*` route needs `portal:access` and goes through `PortalAccessService.child(id)`, which answers 404 for students not linked to the user. Dashboards cache through `CacheStore` (`~/shared/cache`) for 60 seconds.
- **Required DTO fields need `@IsDefined()`**: the global pipe runs with `skipUndefinedProperties`, so a missing field otherwise skips every validator. `PartialType` drops it again for updates.
- **Deleting**: entities with a `@DeleteDateColumn` (students, employees, guardians, academic years, student documents and notes) are soft-deleted by `BaseTenantRepository.deleteById`/`remove`, which keeps the history the PRD requires; their unique business keys are partial indexes (`WHERE "deleted_at" IS NULL`). Other entities are hard-deleted.
- **Constraint races**: "only one" rules (current academic year, primary class teacher, primary guardian) are partial unique indexes as well as service checks; a Postgres unique or FK violation becomes a 409 in `GlobalExceptionFilter`.
- **Rate limiting**: `TenantThrottlerGuard` is a global guard that limits per tenant plus per user or IP.
- **Client IP**: always `req.ip` (or `clientInfoOf(req)`), never the raw `X-Forwarded-For` header. `configureApp` sets Express `trust proxy` from `TRUST_PROXY` (default: loopback and private networks), so only trusted proxies can set the address used by audit rows, sessions and rate limits.
- **Background jobs**: `@nestjs/schedule` (v6; v12 is ESM-only and doesn't load under Jest) is registered in `AppModule` and disabled when `NODE_ENV=test`. Jobs that span schools (e.g. `DomainCheckScheduler`) read through the root connection with `@InjectRepository`; expose a `runOnce()` so tests can drive them.
- **Infrastructure services** (use these, don't hand-roll):
  - Background work: inject `JobQueue` (`~/shared/queue`) and `enqueue(QUEUES.x, name, payload)`; handle it with `@JobHandler(queue, name)` on a singleton provider. Tenant work inside a handler runs through `TenantJobRunner.run(orgId, resolve => …)` (`~/tenancy/tenant-job.runner`) so RLS applies; for user-visible progress use `JobService.start()` + `JobTracker.run()` (`modules/jobs`). Under `NODE_ENV=test` jobs run in-process; tests `await (queue as InlineJobQueue).drain()`.
  - Files: `FileService.upload(file, purpose)` behind the feature endpoint's own permission, with `@UseInterceptors(FileUpload(purpose))` and `requireFile(file)` (`files/file-upload.interceptor`); `FileService.read(id)` gives the bytes to server-side rendering. A job that returns `{ fileId }` gets a signed `downloadUrl` on `GET /jobs/:id`. E2e specs that store files boot with `withMemoryStorage(...)` (`test/support/storage.ts`); purposes and allowed types are in `modules/files/file-purposes.ts`. Hand out `getDownloadUrl()` only after checking access to the owning record.
  - PDFs: `PdfService.render(template, data, { paper })` (`~/shared/pdf`), only from `pdf` queue jobs; `qrSvg(text)` (`~/shared/pdf/qr`) makes an inline QR code (`{{{qr}}}`). Spreadsheets: `buildTemplate` / `parseSheet` / `writeSheet` (`~/shared/spreadsheet/spreadsheet`).
  - Business dates: `SettingsService.today()` is today's `YYYY-MM-DD` in the school's time zone; `localDate`/`addDays` (`~/shared/dates/local-date`) do the arithmetic, and `@IsDateOnly()` (`~/common/decorators/is-date-only.decorator`) validates `date` inputs.
  - Numbers (student IDs, employee numbers, receipts, invoices): `NumberingService.next()` / `nextFormatted()` inside the same `ds.runInTransaction` as the insert that uses the number.
  - Sensitive columns (NID, health, bank): `transformer: EncryptedColumn` (`~/shared/crypto/field-encryption`); never filter or index them.
  - Retryable writes: `@Idempotent()` (`modules/idempotency/idempotent.decorator`). Keys are per user (stored as `<userId>:<key>`).
  - Plans and entitlements (`modules/plans/`, PRD 3.3): gate a feature area with `@RequireModule(PLAN_MODULES.X)` on the handler (403 `MODULE_NOT_IN_PLAN`) and check a quota with `EntitlementService.assertLimit(orgId, 'students' | 'storageMb' | 'users' | 'admins', delta)` (403 `PLAN_LIMIT_REACHED`). A school without a plan is on Free; a running trial grants Standard. New modules go in `plans.catalog.ts` and in the plans that include them (plus a migration for the `plans` rows). Unit tests pass `allowAllEntitlements()`; e2e fixtures that use gated features put their school on Standard (`test/support/plans.ts`).
  - School slugs: the rule, reserved list and `@IsSlug()` are in `~/shared/slug/reserved-slugs`; check availability with `SlugService` (current slugs plus 12 months of `organization_slug_history`). Links to school, apex and admin hosts come from `AppHosts` (`~/shared/hosts/app-hosts`).
  - Setup templates (curriculum, grading, fee heads) are code in `~/shared/templates`; onboarding applies them idempotently through the feature services.
  - School settings (`modules/settings/`, PRD 6.24): read them with `SettingsService.get()` / `getSection('locale')` inside a request (defaults filled in, memoized per request, cached in memory per school for 60 s and invalidated on write), or `OrgSettingsReader.get(orgId)` from a singleton. Don't hard-code what a setting decides (time zone, weekend days, numbering patterns, verify step, lock window, billing day). A new setting is a field on its section in `settings.types.ts` plus its default in `settings.defaults.ts` and its DTO; only the fields a school changed are stored (a stored `null` means cleared), and they merge over the defaults, so no data migration is needed. Each school's `org_settings` row is created with the organization (`OrgSettingsSeeder.createRow`); writes lock it. Nested-object DTO fields need `@IsObject()` (`@ValidateNested` alone accepts arrays).
  - Audit log (`modules/audit/`, global module): auth events, role/permission and member changes, and later financial records, mark changes, attendance corrections and exports call `AuditService.record({ action: AUDIT_ACTIONS.X, entityType, entityId, before, after })` inside the same `ds.runInTransaction` as the change (it writes through the request's tenant connection). Platform actions and platform sign-in events use `PlatformAuditService.record(entry, manager?)` on the root connection. Actor, IP, user agent and request id come from `RequestContext` (`~/shared/request-context`, over `nestjs-cls`; `TenantJobRunner` opens a context per job); pass `actorUserId` only when nobody is signed in yet. Secret keys (`password`, `passwordHash`, `secret`, `otp`, `token`, `*Token`, `*Hash`, `*Secret`) are dropped from `before`/`after`; other keys such as `passMark` stay. Rows are ordered by `created_at` (`clock_timestamp()`) then `seq`. Reading sensitive data (medical records, health notes) is audited too (`student_medical.viewed`, `student_note.sensitive_viewed`), without the data itself. Read with `GET /audit-logs` (`audit:read`) and `GET /platform/audit-logs` (super-admin).
  - Error codes: throw `new XxxException({ message, code: 'SOME_CODE' })`; the error envelope carries `code` for the frontend. New codes go into `doc/error-codes.md` with `npm run docs:error-codes`.
  - Observability (`~/shared/observability`): `reportError(err, { orgId, where })` sends to Sentry when `SENTRY_DSN` is set (5xx and final job failures already do; ids only, never personal data). `GET /api/metrics` is Prometheus text behind `METRICS_TOKEN`. `/api/health` checks the database, Redis (`JobQueue.ping`) and S3 (`StorageService.ping`).
  - Money and numbers shown to people (PDFs, notifications) go through `formatMoney`/`formatNumber` (`~/shared/locale/format`): Bangla digits and lakh grouping follow `locale.numerals`.
  - Uploads: every handler with `FileUpload(...)` also has `@Throttle(UPLOAD_THROTTLE)` (a spec checks it). `helmet()` and `Cache-Control: no-store` are set in `configureApp`.
  - Sign-in slips: `POST /sections/:sectionId/credential-slips` (`modules/credential-slips/`) prints a section's guardian/student slips through `InviteService.issueSlips`, which never touches an account whose owner chose a password. PDFs that need a signature get it from `SettingsService.signatureImages(roles)` (`principal`, `exam_controller`), as data URIs.
  - Data export (`modules/data-export/`, `POST /settings/export`, school admins only): one CSV per table under RLS, so a new tenanted table is exported automatically; columns named like hash/token/secret/password are left out.
- **`.http` files** (e.g. `organization.http`, `auth.http`) next to modules are manual REST-client request samples.

## Frontend architecture

- **Path alias**: `~/*` → `src/*`.
- **Tenant resolution** (`src/lib/tenant.ts`):
  - A subdomain of `NEXT_PUBLIC_ROOT_DOMAIN` resolves to a tenant slug.
  - Custom domains resolve through a backend public endpoint.
  - The apex or `localhost` is the platform host, which shows the platform/super-admin UI under `app/platform/`.
- **Auth** (`src/auth.ts`, `src/auth.config.ts`, `src/proxy.ts`): NextAuth v5 with three Credentials providers: `tenant-credentials`, `platform-credentials` and `handoff`.
  - Session cookies are host-only (Auth.js defaults): each school host, subdomain or custom domain, has its own session. Moving between hosts uses a one-time handoff code: `POST /platform/auth/handoff` issues it, and `app/auth/handoff/route.ts` on the school host redeems it (`POST /auth/handoff`) through the `handoff` Credentials provider. See `doc/domains-and-routing.md`.
  - Don't set `AUTH_URL`, because it breaks multi-subdomain login.
- **API clients**: `src/lib/api/client.ts` (browser) and `src/lib/api/server.ts` (RSC and server actions). Both are built on `createApiClient` in `lib/api/axios.ts`, which injects the bearer token and the `x-tenant-id` header from the session or host, unwraps the envelope, and normalizes errors to `ApiError`.
- **API modules**: endpoint and query hooks live in `src/apis/{platform,tenanted}/<resource>/`. Query keys are in `lib/api/query-keys.ts`.
- **Routes**:
  - `app/(dashboard)`: tenant staff dashboard. Its sidebar is defined in `(dashboard)/_components/sidebar-nav.tsx`. Sidebar items can be role-gated (`lib/sidebar-nav.ts`).
  - `app/student`: student portal.
  - `app/platform`: platform admin.
  - `app/(auth)` and `app/(main)`: auth and marketing pages.
- **`src/features/<domain>/`**: feature UI components. Many are still placeholders.
- **UI and build**: shadcn components live in `src/components/ui` (`components.json`), and antd is also available. The React Compiler is enabled (`reactCompiler: true`).
